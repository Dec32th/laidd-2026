

## 공유결합 도킹 근사(거리 기반) 시도 및 폐기 — 노트북 54

**시도한 것**: 표준 AutoDock Vina 도킹이 공유결합 형성을 반영 못 하는
한계(Michael_acceptor_1/EGFR)를 보완하기 위해, 워헤드 원자가 알려진
반응 잔기(EGFR Cys797 SG, 6JX4에서 실측: (-52.745, -6.415, -17.849))와
반응 가능한 거리(5Å) 내에 도킹되는지 확인하는 기하학적 근사를 시도함.

**실패 원인**:
1. 1차 시도: RDKit SMILES 파싱 순서로 얻은 워헤드 원자 인덱스를 Vina
   출력 PDBQT의 좌표 리스트 인덱스로 그대로 사용 → OpenBabel이 PDB→PDBQT
   변환 시 원자 순서를 재배열해서 완전히 다른 원자를 가리킴을 확인
   (원소 종류 일치율 20/37 = 54%, 우연 수준)
2. 2차 시도: 인덱스 매핑 대신 PDBQT를 mol 파일로 재구성해서 그 안에서
   직접 워헤드 SMARTS 검색 → PDBQT가 결합 차수(단일/이중) 정보를 온전히
   담지 않아 OpenBabel이 워헤드의 C=C 이중결합을 올바르게 추측하지
   못해 매치 자체가 안 됨(실제 공유결합 억제제인 오시메르티닙으로도
   재현 실패)

**결론**: 원자 좌표 기반 그래프 매칭(3D RMSD 정렬 등) 없이는 이 근사를
신뢰성 있게 구현할 수 없음 — 이는 오늘 세션 범위를 넘어서는 별도
작업으로 판단해 폐기. 대신 caveat 문구 강화(도킹 delta가 작다는 것이
공유결합 메커니즘 부재의 증거가 될 수 없음을 critic에게 명시)로
실질적 안전장치는 이미 확보되어 있음(노트북 53에서 완료).


## 다중문제 충돌조정 방식 비교(그리디 vs 리스트순서) — 노트북 56

**비교**: valid set 300개 샘플에서 그리디("남는 문제 수 최소화") vs
원래 방식("리스트 순서대로")를 conflict_resolution 파라미터로 비교.

**결과**: success 214/300(그리디) vs 213/300(리스트순서) — 차이 1건
(0.33%p). 나머지 299건은 두 방식이 동일한 순서를 선택하거나, 순서가
달라도 최종 결과(success/stuck/no_known_fix)는 같음.

**차이 난 1건 분석**(CCCCOC(=O)C(=O)Nc1cccc(-c2nnn[nH]2)c1,
Aliphatic_long_chain + diketo_group 동시 발생): 스텝3까지 동일하게
진행되다 스텝4에서 갈림 — 그리디는 남는 문제가 0개인 diketo_group을
먼저 처리해 바로 성공. 리스트순서는 원래 순서대로 aldehyde를 먼저
처리했다가 그 결과 새로 생긴 het-C-het_not_in_ring 처리에 실패해
stuck으로 끝남. 그리디가 "막다른 골목으로 이어지는 경로"를 정확히
피한 교과서적 사례.

**결론**: 그리디 충돌조정은 이론적으로 정당하고 실제로 의도대로
작동하지만(이 사례가 증명), 다중문제 동시발생 자체가 드물어(300개
중 진단 시점에 문제가 2개 이상인 분자 자체가 소수) 이 규모 샘플에서
실질적 개선 효과는 크지 않음(0.33%p). 전체 valid set(1173개)이나
더 복잡한 분자가 많은 데이터셋에서는 효과가 더 클 수 있음.


## Meeko 기반 covalent docking 가능성 조사 — 노트북 56

**조사 결과**: Meeko는 "PDBQT ↔ RDKit 왕복 시 결합차수 손실 없음"을
공식 지원하며, 이는 노트북 54에서 겪은 원자 매핑 문제(SMILES-PDBQT
인덱스 불일치, OpenBabel의 결합차수 오추정)를 근본적으로 해결할 수
있는 기능임을 확인.

**Covalent docking 지원**: Tethered Docking(2점 고정 공유결합) 방식을
지원 — `--tether_smarts`/`--tether_smarts_indices`로 반응 원자를,
`--rec_residue`로 표적 잔기를 지정. 예: 시스테인 대상이면
`--tether_smarts "SCC" --tether_smarts_indices 3 2`.

**전환 시 필요한 작업 (요약)**:
1. AutoDock Vina → AutoDock-GPU로 도킹 엔진 전환 (Meeko의 covalent
   모드는 Vina를 지원하지 않음)
2. 리간드 준비 파이프라인 재구축 — 표적 시스테인 사이드체인을 포함한
   SDF 파일을 직접 구성해야 함 (지금처럼 SMILES만으로 부족)
3. ProDy 추가 의존성 설치
4. mk_prepare_ligand.py/mk_prepare_receptor.py 새 CLI 학습

**결론**: 방향은 옳으나 별도 세션급 작업(엔진 교체+파이프라인 재구축).
지금 파이프라인(caveat 강화 + 워헤드 반응성 참고표)으로 실질적
안전장치는 이미 확보되어 있으므로, 시간 여유가 생기면 별도
프로젝트로 진행하는 것을 다음 후보로 남김.


## iodine 규칙 재검증 — 예전 결정과의 상충 확인 (노트북 61)

과거 커밋(coverage expansion 세션)에서 "iodine은 alkyl_halide와 100%
redundant"라고 결론 내려 별도 규칙 추가를 보류한 바 있음. 오늘
no_known_fix 재조사 중 다시 검증한 결과, 현재 라이브러리/데이터
기준으로는 iodine이 alkyl_halide와 동시 탐지되는 경우는 3건뿐이고,
11건은 iodine만 단독으로 탐지됨 — 즉 100% 중복이라는 예전 결론은
현재는 성립하지 않음(당시와 라이브러리 상태나 샘플이 달랐을 가능성).
오늘 추가한 iodine 선례(덱스트로티록신/아미오다론 근거)는 이 11건의
실제 gap을 반영하는 것으로, 여전히 유효함. 예전 결정을 그대로 따르지
않고 재검증한 사례로 기록.
