

## 공유결합 도킹 근사(거리 기반) 시도 및 폐기 — 노트북 54

**시도한 것**: 표준 AutoDock Vina 도킹이 공유결합 형성을 반영 못 하는
한계(Michael_acceptor_1/EGFR)를 보완하기 위해, 워헤드 원자가 알려진
반응 잔기(EGFR Cys797 SG, 6JX4에서 실측: (-52.745, -6.415, -17.849))와
반응 가능한 거리(5Å) 내에 도킹되는지 확인하는 기하학적 근사를 시도함.

**실패 원인**:
1. 1차 시도: RDKit SMILES 파싱 순서로 얻은 워헤드 원자 인덱스를 Vina
   출력 PDBQT의 좌표 리스트 인덱스로 그대로 사용 → OpenBabel이 PDB→PDBQT
   변환 시 원자 순서를 재배열해서 완전히 다른 원자를 가리킴을 확인
   (원소 종류 일치율 20/37 = 54%, 우연 수준)
2. 2차 시도: 인덱스 매핑 대신 PDBQT를 mol 파일로 재구성해서 그 안에서
   직접 워헤드 SMARTS 검색 → PDBQT가 결합 차수(단일/이중) 정보를 온전히
   담지 않아 OpenBabel이 워헤드의 C=C 이중결합을 올바르게 추측하지
   못해 매치 자체가 안 됨(실제 공유결합 억제제인 오시메르티닙으로도
   재현 실패)

**결론**: 원자 좌표 기반 그래프 매칭(3D RMSD 정렬 등) 없이는 이 근사를
신뢰성 있게 구현할 수 없음 — 이는 오늘 세션 범위를 넘어서는 별도
작업으로 판단해 폐기. 대신 caveat 문구 강화(도킹 delta가 작다는 것이
공유결합 메커니즘 부재의 증거가 될 수 없음을 critic에게 명시)로
실질적 안전장치는 이미 확보되어 있음(노트북 53에서 완료).


## 다중문제 충돌조정 방식 비교(그리디 vs 리스트순서) — 노트북 56

**비교**: valid set 300개 샘플에서 그리디("남는 문제 수 최소화") vs
원래 방식("리스트 순서대로")를 conflict_resolution 파라미터로 비교.

**결과**: success 214/300(그리디) vs 213/300(리스트순서) — 차이 1건
(0.33%p). 나머지 299건은 두 방식이 동일한 순서를 선택하거나, 순서가
달라도 최종 결과(success/stuck/no_known_fix)는 같음.

**차이 난 1건 분석**(CCCCOC(=O)C(=O)Nc1cccc(-c2nnn[nH]2)c1,
Aliphatic_long_chain + diketo_group 동시 발생): 스텝3까지 동일하게
진행되다 스텝4에서 갈림 — 그리디는 남는 문제가 0개인 diketo_group을
먼저 처리해 바로 성공. 리스트순서는 원래 순서대로 aldehyde를 먼저
처리했다가 그 결과 새로 생긴 het-C-het_not_in_ring 처리에 실패해
stuck으로 끝남. 그리디가 "막다른 골목으로 이어지는 경로"를 정확히
피한 교과서적 사례.

**결론**: 그리디 충돌조정은 이론적으로 정당하고 실제로 의도대로
작동하지만(이 사례가 증명), 다중문제 동시발생 자체가 드물어(300개
중 진단 시점에 문제가 2개 이상인 분자 자체가 소수) 이 규모 샘플에서
실질적 개선 효과는 크지 않음(0.33%p). 전체 valid set(1173개)이나
더 복잡한 분자가 많은 데이터셋에서는 효과가 더 클 수 있음.


## Meeko 기반 covalent docking 가능성 조사 — 노트북 56

**조사 결과**: Meeko는 "PDBQT ↔ RDKit 왕복 시 결합차수 손실 없음"을
공식 지원하며, 이는 노트북 54에서 겪은 원자 매핑 문제(SMILES-PDBQT
인덱스 불일치, OpenBabel의 결합차수 오추정)를 근본적으로 해결할 수
있는 기능임을 확인.

**Covalent docking 지원**: Tethered Docking(2점 고정 공유결합) 방식을
지원 — `--tether_smarts`/`--tether_smarts_indices`로 반응 원자를,
`--rec_residue`로 표적 잔기를 지정. 예: 시스테인 대상이면
`--tether_smarts "SCC" --tether_smarts_indices 3 2`.

**전환 시 필요한 작업 (요약)**:
1. AutoDock Vina → AutoDock-GPU로 도킹 엔진 전환 (Meeko의 covalent
   모드는 Vina를 지원하지 않음)
2. 리간드 준비 파이프라인 재구축 — 표적 시스테인 사이드체인을 포함한
   SDF 파일을 직접 구성해야 함 (지금처럼 SMILES만으로 부족)
3. ProDy 추가 의존성 설치
4. mk_prepare_ligand.py/mk_prepare_receptor.py 새 CLI 학습

**결론**: 방향은 옳으나 별도 세션급 작업(엔진 교체+파이프라인 재구축).
지금 파이프라인(caveat 강화 + 워헤드 반응성 참고표)으로 실질적
안전장치는 이미 확보되어 있으므로, 시간 여유가 생기면 별도
프로젝트로 진행하는 것을 다음 후보로 남김.


## iodine 규칙 재검증 — 예전 결정과의 상충 확인 (노트북 61)

과거 커밋(coverage expansion 세션)에서 "iodine은 alkyl_halide와 100%
redundant"라고 결론 내려 별도 규칙 추가를 보류한 바 있음. 오늘
no_known_fix 재조사 중 다시 검증한 결과, 현재 라이브러리/데이터
기준으로는 iodine이 alkyl_halide와 동시 탐지되는 경우는 3건뿐이고,
11건은 iodine만 단독으로 탐지됨 — 즉 100% 중복이라는 예전 결론은
현재는 성립하지 않음(당시와 라이브러리 상태나 샘플이 달랐을 가능성).
오늘 추가한 iodine 선례(덱스트로티록신/아미오다론 근거)는 이 11건의
실제 gap을 반영하는 것으로, 여전히 유효함. 예전 결정을 그대로 따르지
않고 재검증한 사례로 기록.


## LLM 비결정성 완화(다수결) 파이프라인 통합 — 노트북 62

ask_llm_debate_fix_consistent를 iterative_fix_loop/batch_iterative_fix_loop에
use_consistent_debate 파라미터로 통합 완료(기본값 False, 기존 동작 보존).

## 효과 검증 시도 결과

50개 샘플에서 일반 토의 vs 다수결(n_repeats=3) 토의를 각각 2회 반복
실행해 판정 안정성 비교:
- 일반 토의: 두 실행 간 결과 차이 0/50
- 다수결 토의: 두 실행 간 결과 차이 1/50
- 다수결 소요시간: 약 2.3배(이론상 3배에 근접)

이 샘플에서 토의 자체가 트리거된 횟수가 양쪽 다 3건뿐이라(50개 중
극소수), 위 차이는 통계적으로 유의미한 비교가 아님 — 표본 부족.
노트북 52에서 이미 200~1173개 규모로는 토의가 판정을 유의미하게
바꾼다는 것을 확인했으나, 다수결이 그 변동성을 실제로 줄이는지는
이번 소규모 실험으로는 검증도 반증도 되지 않음. 통합 자체는 완료해
필요시 사용 가능하나, 기본값은 False로 유지 — 대규모(200개 이상)
재검증은 시간/비용 대비 효과가 불확실해 보류.


## 토의 파이프라인 완전해결 비율 재측정 결과 (노트북 66, 자기소개서 준비 중 발견)

기존 기록(67~70%)과 달리, 200개 표본 재측정 결과 완전해결 59.5%로
확인됨. 원인 조사 중 두 가지를 발견:

1. **실제 버그(수정 완료)**: iterative_fix_loop에서 `llm_client`가
   주어지면(토의 모드는 항상 그러함) 다중문제 순서를 정하는 그리디
   충돌조정(conflict_resolution)이 완전히 무시되고
   ask_llm_which_problem_to_fix가 전권을 가져가던 구조적 결함을 발견.
   `use_llm_priority` 플래그를 신설해 우선순위 결정 방식과 토의
   활성화를 독립적으로 제어하도록 수정(기본값 False로 그리디 유지).
2. **버그 아님(설계된 동작)**: 수정 후에도 59.5%가 유지되는 사례를
   추적한 결과, 그리디가 올바른 순서(예: nitro_group 먼저)를 골라도
   ask_llm_which_candidate_to_use가 "이 니트로기는 니트로푸란토인과
   같은 골격으로 활성화 메커니즘 자체가 항균 작용이라 치환 시 약효
   상실 위험이 있다"며 candidate_idx=-1(사람 검토 필요)로 정확히
   보류시키는 경우를 확인. 이는 노트북 62 이후 추가된 워헤드
   참고표/caveat 강화가 누적되며 critic이 더 신중해진 결과로 해석됨.

동점 tie-break 재시도 로직(reverse_tie_order)도 함께 구현했으나,
현재 valid set의 그리디 stuck 15건 전수 조사 결과 tie-break로
구제 가능한 사례는 0건으로 확인(양쪽 순서 모두 실패하는 진짜
stuck). 로직 자체는 정상 작동하며 향후 다른 데이터셋에서 유효할
수 있어 유지.

**최신 수치(재확정)**: 규칙기반 완전해결 74.5%(874/1173, 변동 없음),
토의 파이프라인 완전해결 약 59.5~60%(200개 표본, 그리디 버그 수정
반영, 예전 67~70%보다 낮아진 것은 critic의 보수성 강화가 누적된
결과로 해석). discovery_patterns.md의 사례 1(규칙기반 vs LLM
비교→엔진 결함 발견)과 정확히 같은 유형의 재발견 사례.


## phosphor 규칙의 화학종 3분화 추가 확인 (노트북 66)

기존에 "phosphor는 화학종이 혼재되어 있다"고 기록했던 것을 stuck 67건
분석으로 구체화. BRENK의 phosphor는 P 원자 하나만 있으면 매치되는
매우 넓은 정의인데, 최소 세 가지 서로 다른 화학종이 섞여 있음을 확인:

1. 포스페이트 트리에스터 ((RO)3P=O, P-O 결합만) — 현재 라이브러리의
   problem_smarts([OX2][PX4](=[OX1])([OX2])[OX2])가 겨냥하는 대상.
   그런데도 stuck 67건 중 23건이 이 화학종인데 매치 실패 원인은
   추가 확인 필요(다른 치환 패턴이거나 별도 서브클래스일 가능성)
2. 포스파이트 ((RO)3P, P=O 없음) — 10건, 현재 SMARTS 범위 밖
3. 포스핀 옥사이드 (R3P=O, P-C 직접결합) — 실제 사례 확인
   (NNC(=O)CP(=O)(c1ccccc1)c1ccccc1), 현재 SMARTS 범위 밖

세 화학종 각각 화학적으로 다른 치환 전략이 필요하며(포스페이트는
에스터 가수분해, 포스파이트/포스핀옥사이드는 별도 설계 필요),
ChEMBL 검증을 포함한 본격적인 확장 작업이 요구됨. 시간 관계상
이번 세션에서는 착수하지 않고 다음 확장 작업 후보로 기록.
phosphor(67건, stuck 중 최다), Oxygen-nitrogen_single_bond(33건,
no_known_fix 중 최다)가 우선순위 후보.


## phosphor 화학종 확장 시도 — 음이온 허용은 완전 해소로 이어지지 않아 원복 (노트북 67)

stuck 최다 원인(67건)인 phosphor 규칙을 조사한 결과, 세 화학종
(포스페이트/포스파이트/포스핀옥사이드) 혼재를 확인. 포스페이트
그룹(18건) 중 5건이 음이온 산소([O-], 인산기의 생리적 짝염기 형태)
때문에 problem_smarts([OX2] 요구)와 매치 실패하는 것을 발견해
[OX1,OX2]로 확장 시도.

확장 후 실제 치환을 실행해보니, cleave_bond 1회 실행 후 P-H를 가진
모노에스터 중간산물(R-O-[PH](=O)[O-] 형태)이 생성되고, 이 형태도
BRENK 기준 여전히 phosphor로 재진단되어 완전 해소(success)로
이어지지 못함 — 오히려 stuck 상태가 지속됨을 확인. 이 모노에스터
형태가 화학적으로 안정된 최종형(생체 내 인산모노에스터 유사)인지,
아니면 한 번 더 끊어야 할 위험형인지는 ChEMBL 실조회 검증이
필요하나, 세션 중 ChEMBL API가 서버측 500 오류로 지속 불안정해
검증 불가. 추측에 기반한 candidate 추가를 피하기 위해
problem_smarts를 원래대로 원복하고, 화학종별 확장은 ChEMBL
접근이 안정화된 후 재시도하기로 함. 포스파이트(10건), 포스핀옥사이드
(5건)는 이번 세션에서 아직 착수하지 못함.


## ChEMBL API 불안정 원인 조사 결과 (노트북 67)

phosphor 확장 검증 중 ChEMBL API가 반복적으로 500 에러를 낸 원인을
직접 조사. 같은 요청(molecule/CHEMBL25.json)을 6회 반복한 결과
200/500/타임아웃이 뒤섞여 나옴(500, 200, 타임아웃, 200, 타임아웃,
200) — 특정 엔드포인트나 특정 파라미터의 문제가 아니라 ChEMBL
서버 자체의 간헐적 불안정으로 확인. Colab 환경, 네트워크(와이파이),
우리 쪽 쿼리 코드 문제가 아님을 배제 완료. 재시도 로직(지수
백오프)으로 대응하는 것 외에 근본적 해결책 없음 — 서버가 안정화될
때까지 대기 후 재시도 필요.


## ChEMBL 불안정 원인 최종 확정 — rate limiting (노트북 67 후속)

앞서 "서버 자체의 간헐적 불안정"으로 잠정 결론 냈으나, 요청 간격을
30초로 늘려 재시도한 결과 4/4 100% 성공(응답 헤더 X-ChEMBL-in-cache:
True, retrieval-time 0.04초로 서버 자체는 건강함을 확인). status
엔드포인트도 "UP" 정상. 반면 2~3초 간격의 짧은 반복 요청에서는
500/타임아웃이 섞여 나옴. 즉 원인은 서버 장애가 아니라 짧은 시간
내 과다 요청에 의한 서버측 rate limiting으로 최종 확정. 향후
