# 개발 과정에서 반복된 패턴: 비교/검증 실험이 결함 발견 도구로 기능

학부연구생 지원 및 논문화 논의를 위해 정리. 이 프로젝트 전체에서
최소 4차례 독립적으로 나타난 공통 패턴: '두 방식을 비교하거나
결과를 검증하려 했을 때, 애초 목적(성능 비교/검증)과 다르게
시스템 자체의 숨은 결함을 발견하는 결과로 이어짐'.

## 사례 1: 규칙기반 vs LLM 비교 → 엔진 결함 발견

**설계**: 다중문제 분자 20개에 규칙기반(고정 우선순위)과 LLM
(맥락적 우선순위 판단)을 각각 적용해 최종 결과 비교(ablation).

**표면적 결과**: 세션 초반에는 LLM이 4승 1패로 압도적 우세.

**원인 추적 후 발견**: 격차 5건 중 4건이 규칙기반 엔진 자체의
구현 결함 때문이었음.
- 우선순위 재시도 로직 부재: 최우선 규칙이 propose_fix 단계에서
  실패하면 다른 규칙을 시도하지 않고 즉시 stuck 처리
- 고리치환(replace_ring) 조각화 버그: anchor 외 추가 치환기가
  있으면 고아 원자가 남아 분자가 조각남

**결함 수정 후 재실행**: 3회 반복 재실행 결과 규칙기반이 오히려
3승 0패로 근소 우위(17/20 최종상태 동일, 나머지는 규칙기반 우세).

**의미**: '비교 실험에서 한쪽이 우세하다'는 결과를 그대로 받아들이지
않고 원인을 추적함으로써, 실제로는 LLM의 우수성이 아니라 엔진
자체의 결함이 격차를 만들고 있었다는 것을 밝혀냄. 이후 자동승인
0%라는 3-agent 배치검증 결과와도 같은 방향(시스템이 과확신을
피하도록 설계됨)으로 해석됨.

## 사례 2: 도킹 근거 제공 → critic의 표적 오귀속 편향 발견

**설계**: Michael_acceptor_1 규칙이 걸린 분자에 EGFR 도킹 결과를
critic 판단 근거로 제공(정량적 증거를 주면 판단이 개선될 것이라는
가설).

**발견**: EGFR은 이 규칙의 유일한 등록 표적일 뿐 특정 분자와의
실제 관련성 근거는 없었는데, critic이 도킹 점수만 보고 '이 분자는
EGFR 표적이다'라는 근거 없는 서사를 매번 자동 생성.

**수정**: DOCKING_TARGETS에 caveat 필드를 추가해 표적 특이성
근거 유무를 critic 프롬프트에 명시.

**의미**: LLM에게 정량적 도구(도킹) 출력을 근거로 제공하면, 그
출력의 실제 적용 범위를 넘어서 과확신에 찬 설명을 만들어내는
경향이 관찰됨. 이는 '증거 기반 판단'을 시키더라도 증거의 유효
범위를 명시적으로 제약하지 않으면 오귀속이 발생할 수 있음을
보여주는 사례. LLM-as-judge/tool-augmented LLM 신뢰성 연구와
맞닿는 지점.

## 사례 3: 공유결합 억제제 검증 → 표준 도킹의 방법론적 한계 노출

**설계**: Michael_acceptor_1의 '공유결합 억제제는 예외로 취급해야
한다'는 경고가 실제로 타당한지, EGFR-오시메르티닙 사례로 검증.

**결과**: 표준(비공유) Vina 도킹으로는 원본과 워헤드 환원 버전의
결합 스코어 차이가 거의 없음(+0.05 kcal/mol). 오시메르티닙의
실제 약효는 Cys797과의 공유결합에서 나오는데, 이는 일반 도킹
스코어로 포착되지 않는 상호작용이기 때문.

**의미**: 검증하려던 가설(공유결합 억제제는 다르게 취급해야 함)
자체는 옳았지만, 검증에 쓴 도구(표준 도킹)가 애초에 이 현상을
측정할 수 없는 도구였다는 것을 발견. 이후 Meeko+AutoDock-GPU
기반 tethered covalent docking으로 근본적으로 재도전해 성공
(오시메르티닙 -5.31 vs 이타콘산 +7.06 kcal/mol).

## 사례 4: SMARTS 확장 시도 → 안전성 회귀(과산화물 생성) 발견

**설계**: Aliphatic_long_chain 규칙의 SMARTS를 FilterCatalog
원본에 맞춰 확장(탄소만이 아니라 에테르 산소도 포함하는 사슬).

**발견**: 확장된 SMARTS에 맞춰 치환을 시도하자, insert_atom이
이미 존재하는 산소 바로 옆에 새로운 산소를 삽입해 과산화물
(O-O 결합, 불안정하고 위험한 작용기)을 생성하는 심각한 안전성
회귀가 나타남. insert_atom_multi_chain에는 과산화물 방지 로직이
있었으나 insert_atom에는 누락되어 있었음.

**대응**: 제출 임박 시점에서 두 로직을 모두 안전하게 재검증하기엔
시간이 부족하다고 판단, 원래의 안전한 순수탄소 SMARTS로 원복.
이 확장은 여전히 유효한 개선 방향이나, 안전장치까지 갖춘 뒤
재시도해야 하는 후속 과제로 명시적으로 기록.

**의미**: '더 정확한 규칙'을 추구하는 과정이 오히려 더 위험한
결과를 만들 수 있음을 실제 코드 레벨에서 확인. 개선 시도 자체를
포기하지 않되, 안전 마진이 확보되지 않은 상태에서는 정직하게
원복하는 판단을 내림.

## 공통점: 왜 이런 패턴이 반복됐는가

네 사례 모두 다음 구조를 공유한다:

1. 특정 개선/검증을 시도(비교 실험, 근거 제공, 가설 검증, 규칙 확장)
2. 결과가 기대와 다르거나(사례 1, 4) 기대와 맞아떨어지되 과정에서
   이상 징후가 관찰됨(사례 2, 3)
3. 이상 징후를 원인까지 추적(단순히 '이런 결과가 나왔다'에서
   멈추지 않음)
4. 추적 결과 시스템 자체의 결함이나 도구의 한계를 발견
5. 근본 수정 또는 (근본 수정이 시간상 불가능하면) 정직한 원복/기록

이 구조가 우연히 몇 번 반복된 것인지, 아니면 'LLM+화학도구 결합
시스템'이라는 영역 자체가 이런 종류의 숨은 결함을 유독 많이
만들어내는 구조인지는 아직 결론 내리지 않음 — 논문화한다면 이
질문 자체가 핵심 연구질문이 될 수 있음.

## 논문화 방향 메모 (초안 수준)

가능한 프레이밍: '자동화된 분자 편집 파이프라인 개발에서, 비교
실험과 정량적 검증이 성능 순위를 매기는 도구가 아니라 시스템
결함을 발견하는 도구로 체계적으로 기능한 사례 연구'.

이 프레이밍의 강점: 4개의 서로 다른 층위(엔진 로직, LLM 판단,
도킹 방법론, 화학적 안전성)에서 같은 패턴이 나타나 일반화 가능성
이 있어 보임.

보강이 필요한 부분: 지금까지는 각 사례가 개별적으로 발견/기록된
것이라, '패턴'이라고 주장하려면 (1) 같은 종류의 검증을 더 체계적
으로 반복 수행하거나, (2) 이 패턴이 왜 발생하는지에 대한 이론적
설명(예: 각 구성요소가 독립적으로 검증되지 않은 채 조합되면
이런 결함이 상호작용 지점에서 나타나기 쉽다는 가설)을 세우고
검증하는 추가 작업이 필요.
